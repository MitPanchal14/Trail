## Product outcome

People should be able to describe a messy goal by typing or speaking, then turn it into a meaningful, editable sequence of actions inside the retained Trail UI. Capture → editable transcript/description → Draft my trail → review/edit → Save goal → existing explicit Start/focus/pause/return/completion flow. This is a new-goal assistant, not a chatbot or autonomous agent. Manual creation must remain available without Gemini or a microphone.

The same goal editor should show a compact optional **Describe your goal** section above its manual fields, with a paragraph textarea and microphone control. Keep the existing colours, typography, layout language, home, mountain, Focus, calendar and archive. No chat sidebar, animated AI orb, new onboarding or separate runnable website. New controls use native semantics, clear states and practical 44px targets. At 390px, use natural scrolling without clipped text or horizontal document overflow.

Time estimates and the proposed sequence are planning suggestions. They are not measured effort, scheduled appointments or promises of completion. Keep the word **estimated** visible. Do not convert estimates into earned ascent, timer allocation or completed records. The first slice includes persistent editable per-action estimates and a total/budget comparison, not calendar integration, notifications, automatic replanning or deadline enforcement.

### Server and Gemini contract

- Same-origin POST `/api/plan` accepts bounded JSON with description/deadlineText/availableMinutes only. POST `/api/transcribe` is added in B. Optional GET `/api/ai-status` returns enabled/unavailable capability only, never key/config values. All other write paths remain 405, unknown/private paths 404, HEAD static behavior retained.
- `GEMINI_API_KEY` comes from server process environment. Never ask the user to paste a key into chat; never put one in frontend/localStorage/committed files/logs, request URLs or build output. Respect existing ignored env files; don't overwrite them. Node 20 itself does not imply automatic .env loading: document a supported loading method for the installed Node version, with a blank tracked configuration example if needed. If no key exists, complete offline/mock implementation and report live verification pending. Do not invent live output or route requests through an agent subscription.
- Use one server-configured `GEMINI_MODEL`, not a client-selectable model or base URL. Current official docs list `gemini-3.8-flash` for both audio and structured output; verify actual account access with a bounded live smoke test and use a currently supported Flash model with both capabilities if necessary. Record the actual model/API. No blind old model ID or automatic expensive fallback. Use current documented REST shape; source links below. No SDK needed.
- Fixed HTTPS Google endpoint; x-goog-api-key header; no arbitrary proxy/fetch target or tools. Configure structured output and bounded output tokens; handle refusal, no candidates, invalid structure and provider errors. If using Interactions API, explicitly disable response storage with its supported option; if using another API, document its data behavior. No app transcript/audio persistence or request-body logging; do not claim provider zero retention without evidence.
- Enforce request content type/method, raw streamed body limits (32KB text; B audio limit below), input types/ranges and timeout (about 30s text, 45s audio). Bound provider response reads too. Do not trust only Content-Length. Return sanitized stable 4xx/5xx/503/429 errors without raw provider bodies, prompts, stack traces or secrets; use Cache-Control no-store. Missing config leaves manual app functional.
- Validate browser Origin against the known local/configured app origin; no wildcard CORS. Keep loopback binding by default. Add bounded concurrency and simple local per-client rate limits with bounded/expiring bookkeeping; never trust arbitrary forwarded-IP headers. Origin checks are not authentication. Public shared-key abuse/cost controls and host configuration require a separate deployment gate; do not expose this local server publicly or advertise its local limiter as sufficient public protection.
- Provider calls are only explicit requests, no timer checks/polling/retry storms. Automated tests mock fetch. At most three small non-sensitive live requests for initial proof (typed, audio and constrained example as necessary), then stop live calls unless an actual failure needs diagnosis. Do not log secrets or personal user speech.

## Milestone B — real speech capture → editable transcript

Use `getUserMedia` + `MediaRecorder` for an explicit short recording, submitted to Gemini through the server. Do not depend on SpeechRecognition as the sole implementation: browser support/service behavior varies. No continuous listening, Live API, realtime conversation, system/tab capture or paid recording service.

- Click Record explicitly requests microphone access; show clear recording state, elapsed time, Stop and Discard. Max 60 seconds and 2MiB raw audio; stop automatically at client duration/size cap and always stop every media track on Stop/Discard/navigation/mode switch/pagehide/error. Prevent late permission grants/recorder callbacks from restarting capture after cancellation. Release object URLs/buffers as appropriate. No forced permission request on page load.
- Capability-detect supported recorder formats and choose one supported by both browser and the selected Gemini API, e.g. WebM/Opus. Preserve the real container/MIME; never relabel MP4/WebM bytes as WAV. Validate a small documented MIME allowlist server-side. If the browser has no compatible format, explain and keep typing available; record native Safari coverage honestly. No ffmpeg/dependency install or pretending a mocked format proves hardware compatibility.
- Before sending, explain that the short recording goes to Gemini for transcription. Stopping may prepare the recording, but sending must follow a clearly labelled explicit Transcribe action. Discard before upload sends nothing. A bounded JSON/base64 transport is acceptable (<=3MiB complete body, <=2MiB decoded bytes; reject malformed base64/MIME/empty payload); do not upload via Files API or save recordings to disk.
- Request faithful transcription only, preserving uncertainty rather than filling missing speech with invented tasks. Treat speech as data, not commands to the app. Silence/no clear speech returns a useful empty-speech state, not a fabricated description. Test this limitation; an LLM transcript is not guaranteed verbatim.
- The returned transcript populates an editable description, **not saved actions**. Preserve typed text if it changed while transcription was running; show the transcript separately with explicit insert/replace choice. User corrects it and separately chooses Draft my trail. No auto-generation/API chaining from a recording callback. Cancel/failure keeps prior text and manual creation usable. Non-English speech can retain the user's language; actual language/accent quality is evidence, not assumed support.
